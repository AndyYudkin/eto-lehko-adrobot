# AdRobot — тестовое задание: создаватель кампаний и редактор офферов Keitaro

Дата: 2026-11-19

## Зачем

Тестовое задание. Keitaro — рекламный трекер: принимает переходы по ссылкам, редиректит по правилам (потокам) и считает статистику. Нужно показать умение работать с Keitaro Admin API и воспроизвести логику существующего внутреннего редактора офферов («кнопки работают, цифры верные»). Интерфейс — на наш вкус.

Работаем с **реальным инстансом Keitaro** (доступ и API-ключ есть).

## Цели

1. **Создаватель кампаний.** Форма: название, гео (список кодов стран), оффер (поиск с автокомплитом). По Create создаётся кампания в Keitaro:
   - домен, группа и источник проставлены;
   - поток 1: фильтр `country` по указанным странам → редирект на google.com;
   - поток 2: всех остальных → выбранный оффер (100%).
2. **Редактор существующей кампании.** Добавление/удаление офферов в потоках с корректным пересчётом долей, черновик, отправка в Keitaro.

## Не цели

- Статистика и тренды по офферам (колонки Stats/Trends из видео — не делаем).
- Кнопка SHOW ALL OFFERS из видео.
- Регистрация, роли, мультипользовательность, деплой (есть только простой логин одного пользователя из `.env`).
- Ручной ввод процентов (в оригинале его нет).

## Анти-цели

- В Keitaro не должна уйти сумма долей ≠ 100.
- Изменения не должны уходить в Keitaro без явного PUSH.

## Ограничения

- Стек: FastAPI + SQLAlchemy + Postgres, фронт на React.
- Домен в Keitaro работает только если его DNS указывает на трекер — свой домен не заводим, используем существующий в инстансе.

## Подходы

- **A. Локальная копия + черновики в Postgres** — выбран. Бэк хранит потоки и офферы кампании, историю офферов потока (для показа удалённых) и черновик. Так устроен оригинал (локальные UUID, кнопка Fetch, черновик с Push/Cancel), и у Postgres есть настоящая роль.
- **B. Тонкий прокси над API, черновик во фронте** — отклонён: не может показать офферы, удалённые в самом Keitaro (нет истории), черновик теряется при перезагрузке, Postgres не нужен.

## Часть 1. Создаватель кампаний

**Вход (по ТЗ):** название, гео, ID оффера. Других полей в форме нет.

- **Гео** — список ISO-кодов (`MX,AU,RO`): в ТЗ «гео-код страны», в макете список; список покрывает оба.
- **Оффер** — выпадающий список с поиском. Офферы хранятся в Postgres (таблица `offers`: `kt_id`, `name`, `state`), поиск в Keitaro не ходит. `GET /api/offers?q=` → `[{id, name}]`: только `state == "active"`, `q` содержится в `name` без учёта регистра или равен `id`; пустой (или из одних пробелов) `q` → `[]`; лимита нет.
- **Синхронизация офферов** (`sync_offers`): `GET /admin_api/v1/offers` целиком (серверного поиска в Keitaro нет), upsert по `kt_id`, офферы, которых больше нет в Keitaro, удаляются из таблицы. Запускается после успешного логина (фоновой задачей после ответа; ошибка Keitaro логин не валит: пишем в лог, работаем со старыми данными) и при Fetch from KT в редакторе. Названия офферов в редакторе берутся из этой таблицы. Поле `archive` у оффера — путь к файлам локального оффера, не признак архивности.
- **Домен, группа, источник** — из конфига по названию (`KT_DOMAIN`, `KT_GROUP`, `KT_TRAFFIC_SOURCE`; по умолчанию `kylovoa.com`, `FORTESTS`, `FORTESTS`). Бэк находит ID через `GET /domains`, `GET /groups?type=campaigns`, `GET /traffic_sources`. Домен, группа или источник не найдены → 400 с понятной ошибкой (например, «В Keitaro нет группы FORTESTS»), кампания не создаётся. Сами мы их не создаём. Правила поиска (по схемам ответов из документации):
  - **Домен** (`GET /domains`): сравниваем `name` без учёта регистра, срезав `http(s)://` и `/` с обеих сторон; только `state == "active"` (найден, но не активен → 400 «Домен … в Keitaro не активен»). `KT_DOMAIN` пуст → первый активный. `is_ssl` определяет схему ссылки кампании: `true` → `https://`, иначе `http://`.
  - **Группа** (`GET /groups?type=campaigns`): группы общие для кампаний, офферов и лендингов, поэтому дополнительно фильтруем у себя `type` = тип групп кампаний и `name == KT_GROUP`.
  - **Источник** (`GET /traffic_sources`): `name == KT_TRAFFIC_SOURCE`, только `state == "active"`.
  
  Сверяются на инстансе: значение `type` у групп кампаний (`campaigns`/`campaign`), значения `state` у источников.
- **Префикс названия** — `CAMPAIGN_NAME_PREFIX` из `.env` (у нас `test_iudkin_`, так принято на общем тестовом инстансе) приклеивается к введённому названию: `campaign1` → `test_iudkin_campaign1`; если название уже начинается с префикса, он не дублируется; пустой префикс — название как есть. В Keitaro и в нашей БД хранится полное название. Учесть: Keitaro не даёт переиспользовать название удалённой (архивной) кампании.
- **Проверка оффера** — до любых запросов в Keitaro, по таблице `offers`: нет такого ID или он не `active` → 400 «Оффер #<id> не найден или не активен».
- **Создание кампании:** `POST /campaigns` с минимумом полей: `{name, alias, type: "position", state: "active", domain_id, group_id, traffic_source_id}`; остальное (`cost_*`, `parameters`, `postbacks`, …) — по умолчанию Keitaro. `group_id` шлём числом (в схеме запроса он `string`, в ответе — число; считаем это ошибкой документации). Из ответа берём `id` (→ `kt_id`) и `alias` (именно из ответа). `domain_id` в ответе нет, поэтому ссылку кампании `https://<домен>/<alias>` собираем из найденного ранее домена и храним в `campaigns.url`.
- **Потоки:** два `POST /streams`, оба `type: "regular"` (при ротации по позиции проверяются по порядку), `state: "active"`, `weight` не шлём:
  1. `position: 1`, `name: "Geo → Google"`, `schema: "redirect"`, `action_type: "http"`, `action_payload: "https://google.com"`, `filters: [{"name": "country", "mode": "accept", "payload": [гео]}]`;
  2. `position: 2`, `name: "Offer"`, `schema: "landings"`, без фильтров, `offers: [{"offer_id": <id>, "share": 100, "state": "active"}]`.
  
  Формат подтверждён по потокам существующих кампаний на инстансе (2026-11-19, 30 кампаний): редирект — `schema: "redirect"`, `action_type: "http"`, URL строкой в `action_payload` (в `action_options` — нет); фильтр страны — `{"name": "country", "mode": "accept"}`. Поток с офферами у других бывает и `type: "default"`, и `"regular"` — оставляем `regular`.
- **Тестовый пользователь видит один оффер** (`18813 Flexacil …`) — так выдан доступ всем кандидатам; на нём же собраны чужие кампании. Это не баг синхронизации.
- Если создание потока упало — кампанию не оставляем полусозданной: пытаемся удалить её и возвращаем ошибку.
- После успеха кампания сохраняется в Postgres (наш UUID + ID в Keitaro), сразу делается fetch её потоков.

**UI (макет: https://claude.ai/artifact/Ep76KEGV4ayqrow6ek5AkY, артборды «Campaigns list» и «New campaign dialog»):**
- Сначала экран логина (артборд «Login»): поля Login и Password, кнопка Log in. Один пользователь, логин и пароль из `.env` (`APP_LOGIN`, `APP_PASSWORD`), регистрации нет. Пользователь хранится в таблице `users` (`id`, `login` unique, `password_hash`, `created_at`): при старте бэка пароль из `.env` хешируется bcrypt и делается upsert по логину; все прочие пользователи удаляются, так что в таблице всегда ровно тот, что в `.env` (смена логина/пароля в `.env` вступает в силу после перезапуска). Открытый пароль живёт только в `.env`: ни в БД, ни в логах. В шапке списка — Log out.
- **Токены.** Access — JWT HS256 (ключ `JWT_SECRET`), `sub = user_id`, живёт 15 мин (`ACCESS_TTL_MIN`), проверяется без БД. Refresh — `secrets.token_urlsafe`, живёт 7 дней (`REFRESH_TTL_DAYS`); в таблице `refresh_tokens` (`id`, `user_id` → users cascade, `token_hash` sha256, `expires_at`, `revoked_at`) хранится только хеш. Оба — в `httpOnly`, `SameSite=Lax` cookie (`Secure` — при `COOKIE_SECURE=true`); access на `Path=/api`, refresh на `Path=/api/auth`. Браузер сам прикладывает их к запросам, фронт токенов не видит.
- **Эндпоинты.** `POST /api/auth/login {login, password}` — ищет пользователя, `bcrypt.checkpw`, ставит обе cookie (204); неверный логин или пароль → 401 «Invalid login or password» (одинаково). Для неизвестного логина bcrypt всё равно выполняется против фиктивного хеша — время ответа не выдаёт, какой логин существует. `POST /api/auth/refresh` — валидный refresh → отзывается, выдаётся новая пара (ротация); повтор уже ротированного refresh в течение 10 с — нормален (две вкладки обновились одновременно), выдаём новый; позже 10 с → признак утечки: удаляем все refresh пользователя и 401. `revoked_at` ставит только ротация, logout удаляет строку; истёк/не найден → 401. `POST /api/auth/logout` — отзывает refresh, стирает cookie (204). `GET /api/auth/me` → `{login}`.
- **Auth guard на бэке.** Зависимость `current_user` (access из cookie, подпись + `exp`, иначе 401) висит на общем роутере `/api`, в который включены все роутеры приложения; без неё — только `/api/auth/*` и `/api/health`. Новый эндпоинт по умолчанию закрыт.
- **Фронт.** `api.ts` на 401 один раз зовёт `/api/auth/refresh` (параллельные запросы ждут один общий refresh) и повторяет запрос; refresh тоже 401 → `/login`. Route guard на фронте — только для удобства, защищает бэк.
- Без вкладок. После логина — список кампаний (новые сверху): название, ссылка кампании, гео, число офферов; действие Edit offers (кнопки View in KT в списке нет). Справа сверху кнопка New campaign.
- New campaign открывает диалог поверх списка: Name, Geo (чипы, вставка `MX,AU,RO` разбивается на коды), Offer (автокомплит по ID и названию), блок «Will be created» (только два потока; домен/группу/источник в UI не показываем — бэк проставляет их из конфига молча), Cancel / Create.
- После Create диалог закрывается, кампания просто появляется первой в списке. Отдельного экрана успеха нет.
- **README:** отметить, что по ТЗ указанное гео уходит на Google, а остальные — на оффер (выглядит инвертированным относительно обычной практики), сделано буквально по тексту.

## Часть 2. Редактор кампании

### Экраны

- **Список кампаний** (он же стартовый экран, см. часть 1) — кампании, созданные нашим создавателем (хранятся в Postgres). Чужих кампаний под нашим API-ключом не ожидается, импорт произвольных кампаний из Keitaro не делаем. Если кампанию удалили в Keitaro, fetch возвращает понятную ошибку, и кампанию можно убрать из локального списка.
- **Редактор** — вверху одна кнопка на всю кампанию: `Fetch from KT`, пока черновик пуст; `Push to KT` и рядом `Cancel`, как только хоть в одном потоке есть правки. Ниже — потоки: сначала потоки с офферами, затем потоки без офферов (как в оригинале: Flow 2 выше Flow 1), внутри группы — по позиции. Заголовок потока: имя, позиция, ID потока. Потоки без офферов (редирект на Google) показываются только для чтения: фильтр по странам и URL редиректа, без Add/Remove.
- Строка оффера: название, доля %, булавка, кнопка `Remove` (или `Bring back` для удалённого). Внизу потока — выбор оффера + `Add`.
- Поток с несохранёнными изменениями подсвечен, в заголовке пометка «unsaved changes» и, если его нельзя отправить, подсказка почему.
- Порядок строк: активные по доле по убыванию, удалённые — в конце, серые, с пометкой «removed» и 0%.

### Состояние оффера в потоке

Для каждой пары (поток, оффер), которая когда-либо была в потоке:

| поле | смысл |
|---|---|
| `synced_active`, `synced_share` | что сейчас в Keitaro (по последнему fetch/push) |
| `active`, `share` | черновик |
| `pinned` | булавка (только локально, в Keitaro её нет) |
| `position` | порядок в потоке (для раздачи остатка при округлении) |

Поток «грязный», если хоть у одного оффера черновик ≠ synced.

### Действия

- **Fetch from KT** — сначала синхронизирует офферы (`sync_offers`), затем тянет потоки и офферы кампании. Оффер есть в Keitaro → активен, доля из Keitaro. Был у нас, но нет в Keitaro → удалён (в т.ч. если удалили в самом Keitaro). Новый в Keitaro → заводим активным. Булавки сохраняются. Пока есть черновик, кнопки Fetch нет — сначала Push или Cancel.
- **Add** — оффер (новый или ранее удалённый) становится активным, незакреплённым → пересчёт.
- **Remove** — `active=false`, доля 0, булавка снимается → пересчёт.
- **Bring back** — как Add.
- **Pin / Unpin** — Pin фиксирует текущую долю (пересчёт не нужен: сумма и так 100). Unpin возвращает долю в общий котёл и запускает пересчёт: A закреплён 40, B/C 30/30 → снять булавку с A → 34/33/33.
- **Push to KT** — на всю кампанию: у каждого изменённого потока проверка суммы = 100 (если хоть один не проходит — не отправляется ничего); затем потоки кампании читаются из Keitaro, и если у изменённого потока там уже не то, что мы видели при последней синхронизации (кто-то поменял его в админке), Push отказывает с 409 «нажмите Cancel, затем Fetch» — иначе PUT молча стёр бы чужие правки; затем `PUT /streams/{id}` по каждому изменённому потоку с активными офферами и их долями (формат `{"offers": [{offer_id, share, state: "active"}]}` проверен на инстансе 2026-11-19: доля меняется, ответ 200), затем кампания перечитывается из Keitaro (synced := то, что там теперь).
- **Cancel** — на всю кампанию: черновик := synced; офферы, которых в Keitaro не было, исчезают.

### Пересчёт долей (главная логика, покрыта тестами)

Чистая функция над активными офферами потока:

1. Закреплённые сохраняют долю.
2. `R = 100 − сумма закреплённых`, `n` — число незакреплённых.
3. Каждому незакреплённому `R // n`, ещё по 1 — первым `R % n` по `position`.

Примеры: 3 оффера → 34/33/33; 4 → 25×4; B закреплён на 33 + A, C, D → 23/22/22.

Крайние случаи:
- `n = 0` и сумма закреплённых ≠ 100 (удалили закреплённый, остальные закреплены) — пересчёт ничего не меняет, Push заблокирован с подсказкой «открепите оффер».
- Закреплённые дают 100 — незакреплённые получают 0; сумма корректна, Push разрешён.

## Архитектура

- **Backend:** FastAPI, SQLAlchemy 2 (async), таблицы создаются при старте бэка (`Base.metadata.create_all`; миграций нет — проект разворачивается один раз на чистой базе, при смене схемы базу пересоздают: `docker compose down -v`), httpx-клиент Keitaro отдельным модулем, Pydantic-настройки из `.env` (`KT_URL`, `KT_API_KEY`, домен/группа/источник).
- **Frontend:** React + TypeScript + Vite, TanStack Query.
- **Тесты:** pytest; функция пересчёта — таблица кейсов; сервисы редактора и создавателя — с замоканным Keitaro (respx).
- **Запуск:** docker-compose (postgres, backend, frontend).

### API бэка (черновой)

- `GET /api/offers?q=` — поиск офферов
- `POST /api/campaigns` — создать кампанию `{name, geo: [..], offer_id}`
- `GET /api/campaigns` — наши кампании (из Postgres)
- `DELETE /api/campaigns/{id}` — убрать из локального списка
- `POST /api/campaigns/{id}/fetch` — синхронизация с Keitaro
- `GET /api/campaigns/{id}/streams` — потоки с офферами (черновик)
- `POST /api/streams/{id}/offers` `{offer_id}` — add / bring back
- `DELETE /api/streams/{id}/offers/{offer_id}` — remove
- `PATCH /api/streams/{id}/offers/{offer_id}` `{pinned}` — булавка
- `POST /api/campaigns/{id}/push`, `POST /api/campaigns/{id}/cancel`
